## The piece

- **Why:** the app looks busier than it is because every screen styles
  itself. Counted on 24 November 2026: 1,014 `setStyleSheet` calls in
  `src/ui`, about 170 different colour values, and buttons in many sizes
  and colours on the same screen. U.1 built the shared parts
  (`src/ui/ui_kit.py`: `PALETTE`, `primary_button`, `compact_button`,
  `section_header`, `card`, `status_chip`, `empty_state`); most screens do
  not use them yet.
- **The writer gets:** a calmer, sleeker app with nothing moved. On every
  screen:
  - **One main button.** The action the screen is for uses
    `primary_button`. Every other button is plain. A screen never shows two
    coloured buttons side by side.
  - **One set of colours.** Text, soft text, borders, success, warning and
    error come from `PALETTE`. Flag colours come from `FLAG_COLOURS` and
    stage colours from `STAGE_COLOURS`, so a colour means the same thing
    everywhere.
  - **One spacing.** The same margins and gaps inside panels and dialogs,
    from constants in `ui_kit` (add them there if they are missing).
  - **Section headings and empty states** use `section_header` and
    `empty_state`, so a panel with nothing in it says so in one quiet line
    instead of showing empty boxes.
  - **Icons and emoji in labels:** at most one per label, and the same one
    for the same action everywhere. The words never change, so nothing a
    writer has learned moves.
- **Do, a screen at a time, most used first:** Write and its side panel, the
  Companion, the Critique, Settings, then the rest. For each: screenshot,
  replace inline styles with the shared parts, screenshot again, compare.
  A screen that would need restructuring to comply is listed in *Outcome*
  and left alone.
- **Limit: appearance only.** No control is added, removed, renamed, moved
  or resized beyond its padding. No behaviour changes. Object names used by
  tests or style rules stay.
- **Rule 14:** files over 3,000 lines get replacements of existing style
  lines only, never new blocks. The net line count of each file touched
  goes down; say by how much in *Outcome*.
- **Repeatable.** One session will not finish 1,014 calls. Do the most-used
  screens, record what is left, and run the piece again.
- **Dark mode is not in this piece.** Moving colours to `PALETTE` makes it
  possible later; say in *Outcome* what would still be in the way.
- **Tests:** a test that fails if a file already cleaned gains a new
  hard-coded colour value outside `ui_kit`. The harness's counts must not
  change at all (this piece moves nothing).
- **Done when:** the screens named above take every colour and button style
  from `ui_kit`, and before-and-after screenshots show the same controls in
  the same places.

## Nothing cut, nothing lost (applies to every item above)

- **No feature is removed.** The piece starts with a capability checklist:
  every button, link, menu entry and shortcut on each screen it touches, and
  where each is afterwards. Nothing is ticked off as "gone". An action that
  moves is at most one click further away, and its keyboard shortcut and its
  old menu entry still work.
- **Display only.** This piece changes what is shown and where. It does not
  change `save_project`, `load_project`, the chapter files, or any stored
  file's names, places or layout (rule 15). Text still reaches a chapter
  only through the editor's existing path.
- **Updating is safe in both directions.**
  - A project, settings file or window layout written by the version before
    this piece opens after it with nothing missing and no prompt.
  - Settings keys that are no longer used are left in place and ignored,
    never deleted or rewritten, so going back to the older version of the
    app finds everything as it left it.
  - Any new setting has a default that reproduces today's behaviour for an
    existing project or an existing install, unless the brief says the
    writer chose otherwise.
- **Proof, not promise.** Before and after: the safety check from
  [0.3](03-0.3-safety-net-for-your-two-projects.md) on both of the writer's
  projects (run on copies; tests never touch real work), and the harness
  counts. A test opens a project and a settings file saved before the piece,
  and checks that the chapter text is byte-for-byte the same after open,
  save and reopen.
