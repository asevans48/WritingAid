## The piece

- **Why:** the app stops the writer with a box for things that need no
  answer. Counted on 24 November 2026: 329 `QMessageBox.information` calls
  in `src/ui`. Each one is a click that does nothing.
- **The writer gets:** a message that only informs appears quietly (in the
  status bar, or as a line on the screen it concerns) and goes away by
  itself. A box still appears for anything that needs a decision or that the
  writer must not miss.
- **Sort every information box into three kinds first,** and put the table
  in *Outcome* before changing any:

  | Kind | Example | Becomes |
  |---|---|---|
  | **Done, nothing to decide** | "Saved", "Exported to …", "Copied" | A status-bar message for a few seconds; where a file was written, the message keeps a "Show file" link |
  | **Nothing to do** | "No issues found", "Select some text first" | A quiet line on the screen itself (`empty_state` or the screen's status label) |
  | **The writer must know** | Anything about saving failing, files missing, a model not set up, work that could be lost | **Stays a box. Not touched.** |

- **Never touched:** warnings, errors, questions and confirmations
  (`QMessageBox.warning`, `.critical`, `.question`), and **every message to
  do with saving, loading, backup, recovery, export failing or overwriting.**
  If in doubt, it stays a box.
- **Nothing is lost when a message is quiet.** A new small module keeps the
  last messages of the session, and one entry (Help ▸ Recent messages, or a
  click on the status bar) lists them, so a message that vanished before it
  was read can be read again.
- **A writer who prefers the boxes** gets them back: one switch in Settings,
  "Show a box for every message", off by default.
- **Build:** one function in a new small module, for example
  `notify(window, text, kind="done", link=None)`, which the three kinds
  call. The 329 call sites change one line each. Do the Write tab, the
  Companion and the Critique first, then the rest; this piece is repeatable.
- **Rule 13:** adds one menu entry and one setting; takes away a click from
  each message moved. Say how many were moved.
- **Tests:** a "done" message reaches the status bar and the recent list and
  opens no dialog; a save failure still opens a box; with the switch on,
  every message opens a box as today.
- **Done when:** on the three screens named, no information box appears for
  a message of the first two kinds, and every message can still be read
  afterwards.

## Nothing cut, nothing lost (applies to every item above)

- **No feature is removed.** The piece starts with a capability checklist:
  every button, link, menu entry and shortcut on each screen it touches, and
  where each is afterwards. Nothing is ticked off as "gone". An action that
  moves is at most one click further away, and its keyboard shortcut and its
  old menu entry still work.
- **Display only.** This piece changes what is shown and where. It does not
  change `save_project`, `load_project`, the chapter files, or any stored
  file's names, places or layout (rule 15). Text still reaches a chapter
  only through the editor's existing path.
- **Updating is safe in both directions.**
  - A project, settings file or window layout written by the version before
    this piece opens after it with nothing missing and no prompt.
  - Settings keys that are no longer used are left in place and ignored,
    never deleted or rewritten, so going back to the older version of the
    app finds everything as it left it.
  - Any new setting has a default that reproduces today's behaviour for an
    existing project or an existing install, unless the brief says the
    writer chose otherwise.
- **Proof, not promise.** Before and after: the safety check from
  [0.3](03-0.3-safety-net-for-your-two-projects.md) on both of the writer's
  projects (run on copies; tests never touch real work), and the harness
  counts. A test opens a project and a settings file saved before the piece,
  and checks that the chapter text is byte-for-byte the same after open,
  save and reopen.

## Build notes

_Added 24 November 2026 so a fresh session can finish this piece without searching. Names were checked against the code on that date; if one has moved, find it with a search and say so in Outcome._

- **Read first:** `_status` in `src/ui/revision_controller.py` (the existing
  way to put a line in the status bar); `empty_state` in `src/ui/ui_kit.py`.
- **Where the boxes are** (`QMessageBox.information`, counted 24 November
  2026): `training_tool_window.py` 47, `manuscript_editor.py` 41,
  `video_studio/studio_widget.py` 37, `main_window.py` 24, then the Video
  Studio dialogs.
- **First session:** `manuscript_editor.py`, `companion_panel.py`,
  `grader_widget.py` and `main_window.py` only. The rest in later sessions.
- **Build:** new `src/ui/notify.py` with `notify(window, text, kind, link)`
  and the list of recent messages. With the Settings switch on, it calls
  `QMessageBox.information` exactly as today.
- **Sorting rule, to apply call by call:** read the text and the code after
  the call. It stays a box if the text mentions save, load, backup, recover,
  overwrite, delete, drop, fail, error, cannot, missing or not set up; if it
  is shown before or after anything that writes a file the writer did not
  ask for; or if you are not sure. Put the table of every call and its kind
  in *Outcome* **before** changing code, so the writer can see it.
- **Tests that patch `QMessageBox.information`** will stop seeing the calls
  that moved. Change such a test to check `notify`'s recent list instead,
  and list each changed test in *Outcome* (rule 11 asks for the reason).
- **Stop and report if** more than a handful of tests depend on a box that
  would move; do those screens last.
