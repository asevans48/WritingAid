## Design

_Written 26 November 2026 (8.1a). Waiting for the writer's review; the
open questions are at the end (§17). Names were checked against the code
that day. No code was written._

### 1. In one paragraph

"Check the book with the model…" becomes a **job**: a long read that
belongs to the app, not to the Critique screen. It keeps going while you
write, with the Critique closed or in its own window. A small line at the
right of the status bar shows how far it has got ("📖 Book check · 12 of
40"), on any screen; the scorecard's progress row shows the detail, as
today. **Pause** stops it after the request in hand and keeps everything
done; **Resume** carries on from the next chapter. If the app is closed
or crashes, the job carries on by itself shortly after the project is
next opened. If the model server stops answering part-way, the job
pauses with a plain message, tries again every few minutes, and carries
on by itself when the server is back. One job runs at a time, inside the
app, so it never starts a second copy of the on-device model. A job only
adds results to the readiness file; it never touches a chapter. There is
no new window and no new button.

### 2. What exists today, and what is missing

The whole-book check from 2.3 already does most of the hard part:

- **It saves as it goes.** `readiness.book_report` writes each chapter's
  result to the readiness file (`<project>.readiness.json`, R.7) as soon
  as the chapter is judged, keyed by a fingerprint of the chapter's text
  (`text_hash`).
- **It carries on.** A chapter already judged for its current text is
  not judged again (`use_cache`); `readiness.model_work` counts what is
  left. Stop keeps every finished chapter, and the next run starts where
  the last one stopped. This is tested
  (`test_stopping_keeps_finished_chapters_and_the_next_run_carries_on`).
- **It runs in the background** through the shared helper
  (`background.run_background`, R.2), with Stop and a progress row
  (`ScorecardWidget.refresh`, `_partial`, `_show_progress`,
  `_end_model_run`).

What is missing, and what the queue adds:

| Missing today | What the queue adds |
|---|---|
| The run belongs to the scorecard. If the app closes, nothing remembers a run was going on; you start it again by hand. | A small job file per project remembers that a check is unfinished, and the app carries on with it next time. |
| A server that goes away part-way is treated like a bad reply: every remaining chapter fails one by one, keeps its scan, and the run "finishes" with nothing judged. | The job notices the server has gone, stops sending, says so, and waits for it. |
| Stop is the only control, and progress is only visible on the scorecard. | Pause and Resume (the same button), and a status-bar line on every screen. |
| Two runs could be started for two manuscripts at once. | One job at a time; a second waits its turn. |
| A run that dies leaves no trace. | A line in `~/.creativeos/crash.log` (0.5) and a plain message. |

### 3. Where job state is stored

**One small file per project, beside the project file:**
`<project>.jobs.json` (for example `Teller County.jobs.json` beside
`Teller County.writerproj`), named the R.7 way
(`state_files.own_path(project, "jobs", "jobs")`). A project not yet saved
keeps it in `~/.creativeos/jobs/<name>.json`. **Never the project file.**

**What it holds** (one entry per job, newest last; at most 20 kept, the
oldest finished ones dropped):

| Field | Example | What it is for |
|---|---|---|
| `id` | `book_check-main-20261126-2104` | Telling jobs apart |
| `kind` | `book_check` | Which kind of work (only this one in 8.1b) |
| `scope` | `null` (main manuscript) or a novella's id | Which manuscript |
| `state` | `running`, `paused`, `waiting`, `done`, `cancelled`, `failed` | Where it stands |
| `why` | "You paused it", "The app was closed", "The model server stopped answering" | The plain reason shown to you |
| `model` | `server:gpt-oss-120b` | Which model it was using (shown; see §7) |
| `done`, `total` | `12`, `40` | For the progress line only |
| `current` | "The Cellar" | The chapter last worked on |
| `quiet` | `false` | Started by the background option (§4, row 2) |
| `started`, `updated`, `finished` | times | Shown, and for the crash check (§7) |
| `error` | "Couldn't reach the server at …" | The last problem, word for word |

Plus `format_version: 1` at the top.

**What it does not hold: results.** Results go to the readiness file
exactly as today, through the same calls (`readiness_state.store_chapters`).
The job file only says *that* a job is unfinished and *how it stands*. It
never says which chapters are done in a way anything relies on: the
readiness file is the one record of that (§7). So the two files can never
disagree about what has been judged.

**Safe, as every store is (rules 11 and 15):**
- written only through `safe_store` (a temporary file swapped in);
- a missing or empty file means "no job";
- an unreadable file is set aside under a new name and you are told
  (`safe_store` does this already), never saved over;
- a file stamped with a newer `format_version` is read, never written (as
  `critique_resume` and `readiness_state` do);
- **an older version of the app never reads this file,** so it ignores
  it. It still reads the readiness file, which holds exactly what it holds
  today, so the older app sees every chapter judged so far;
- the test set-up redirects it to a temporary folder (rule 15), like the
  readiness file (`tests/conftest.py`).

**Two projects:** each has its own job file. A job in one project never
reads or writes the other's files.

### 4. Every place that starts a job

| # | Where | What happens |
|---|---|---|
| 1 | **Check the book with the model…** (the link in the scorecard's note, `ScorecardWidget.start_model_check`) | The estimate box as today (`scorecard_model_run.confirm`). **Start** adds a book-check job for the manuscript shown. If another job is running, this one waits its turn and the line says "waits for the Main manuscript check". |
| 2 | **The background option**, "Also judge changed chapters in the background while I write" (`_background_tick`, every 5 minutes, off by default) | Adds a *quiet* job when chapters have changed, as today. Skipped while any job is unfinished (the open job will judge those chapters anyway). Quiet means its progress shows on the scorecard and the status-bar line, but its "done" message is not shown (it is still kept in Help ▸ Recent messages). |
| 3 | **Opening a project** that has an unfinished job | Not a new job: the open one carries on (§7). |
| 4 | **Resume** (the scorecard button, §9) | Carries on a paused or waiting job. |
| 5 | **The server answering again** after it went away (§8) | Carries on a waiting job by itself. |

Nothing else starts one. **Check readiness** (the scan, no model, a few
seconds) stays as it is and is not a job. The detailed critique keeps its
own resume file (`critique_resume.json`) and is not a job in 8.1b. These
were searched for in `src/`: `refresh(judge=True)` is called only from
rows 1 and 2.

### 5. How a job runs

- **Inside the app, never as a separate program.** It runs on a
  background thread through the shared helper (`run_background`, R.2), as
  the 2.3 run does. This is what keeps the on-device model safe (§6).
- **It belongs to the app, not to a screen.** A small job runner is made
  once by the main window. The scorecard and the status-bar line listen to
  it; neither owns it. Closing the Critique's own window, moving to
  another tab, or closing the Improve window does not touch the job.
- **One at a time.** Jobs wait in line in the order they were started.
- **The model** is the Critique's own analysis model, built the way 2.3
  builds it (`task_llm.build_critique_llm`, rule 2). No new setting. With
  no model set up (or AI off), "Check the book with the model…" is not
  shown, as today; if the model has gone between start and run, the job
  does a scan, says "No model is set up, so this was a scan" (2.3's
  words), and finishes (rule 1).
- **The work itself** is the 2.3 work, unchanged: `book_report(project,
  scope, llm=…, stop=…, progress=…, partial=…)`. The job adds three
  things around it: a watcher on the model (§8), a stop that also stops
  when the server has gone, and writing the job file after each chapter.
- **Switching project** with a job running pauses it ("You opened another
  project"); it carries on when that project is opened again. A project
  must be open for its chapters to be read, and nothing a job does in one
  project may reach the other (rule 11).
- **Quitting the app** pauses the job ("The app was closed"). No question
  is asked (open question 1). The request in hand is dropped; the chapter
  it belonged to is judged again next time, so nothing is half-saved.
- **Keeping the Mac awake.** A check started in the evening has to still
  be running in the morning, and macOS puts an idle Mac to sleep. While a
  job is *running* (not paused or waiting), the app asks macOS not to
  sleep, the way the `caffeinate` command does, and lets go as soon as the
  job pauses or finishes. The screen still sleeps; a closed lid still
  sleeps. This is a system helper, not a model, and is the only extra
  process (open question 3).
- **A job that dies** (an error the app did not expect) is marked
  `failed`, with the error in plain words on the scorecard ("The book
  check stopped with an error. Chapters already judged are kept.") and a
  dated line in `~/.creativeos/crash.log`. Resume starts it again.

### 6. The on-device model: never two at once

**What happened.** On 24 November a measurement script was run while the
app was using the on-device (MLX) model. Two programs drove the graphics
processor at once, and the app crashed with a Metal GPU timeout (P.4's
*Outcome*, decision 12).

**Why the app on its own is safe.** Inside one program, every on-device
request already takes a single lock (`mlx_utils.MLX_GENERATE_LOCK`, used
by `llm_client._generate_mlx_local` and the rest), so two features take
turns, and the shared loader never loads a second copy of a model already
in memory (`mlx_utils.load_mlx_model`). The danger is a *second program*.

**So the queue's rules are:**
1. **A job runs inside the app.** It never starts a second program to do
   model work (no helper process, no script). Only one copy of the
   on-device model can ever be in use, and the lock is shared.
2. **One job at a time,** so a job never competes with another job.
3. **A job gives way to you.** With an on-device model, after each
   request the job lets go of the model and waits a second before the
   next, so anything you ask for (Rephrase, Suggestions, the chat) goes
   first. At worst you wait for the one request the job has in hand
   (about 15 to 45 seconds on the on-device model, from 2.3's estimate).
   On the server or a cloud model there is nothing to share; the job does
   not wait.
4. **A job never loads the on-device model at start-up.** When a job
   carries on after a restart (§7), it waits two minutes after the project
   opens, so your first actions come first.

**What the queue cannot stop:** a script started from the Terminal while
the app has the on-device model in memory. Decision 12 stands for scripts
(run them with the app closed). Open question 7 proposes a small guard for
that, as its own piece.

**Jobs on the on-device model, or only on the server?** The brief offers
both. This design allows any model, because the rules above make it safe
and the overnight check is useful on a laptop too; open question 4 asks
you to confirm.

### 7. Resuming after a restart

**What "resume" reads:** the job file says *a book check for this
manuscript is unfinished, and whether you paused it*. The readiness file
says *which chapters are already judged for their current text*. Resume
simply runs the 2.3 work again for that manuscript: chapters already
judged come from the readiness file instantly, and the model starts on
the first chapter that is not. That is "carries on from the next
chapter". Nothing is taken on trust from the job file's `done` count.

**When the project opens:**

| The job file says | What happens |
|---|---|
| `running` or `waiting`, and the app was closed normally ("The app was closed") | Two minutes after the project opens, the job carries on by itself. The status-bar line says "Book check carries on in 2 minutes · 12 of 40" meanwhile (open question 1). |
| `running`, but the app did not close normally (no "closed" stamp) | The same, and a line goes in `crash.log`: "The book check for Main manuscript was interrupted at chapter 13 of 40 (the app did not close normally)." |
| `paused` because **you** paused it | Stays paused. The scorecard shows "Paused at chapter 12 of 40 · Resume". |
| `done`, `cancelled` or `failed` | Nothing runs. A finished check you have not yet looked at shows "✓ Book check done" in the status bar until you click it. |

**Chapters changed in the meantime** are simply chapters not judged for
their current text, so they are judged in their turn. **A different
model** (you changed the Critique's model while it was paused) is used
from then on; the scorecard says "Carrying on with <model>" once.

### 8. When the model can't be reached part-way

**Noticing.** Today a failed request is caught inside the checks (for
example `readiness_judge.judge_stage`) and the chapter quietly keeps its
scan. The job wraps the model it hands to the checks in a thin watcher
that passes every request through unchanged but notes when one fails
because the model **could not be reached**: the server's own
`model_server.ServerError` caused by a connection failure or a time-out
("Couldn't reach the server at …", "The server didn't answer within …"),
and for a cloud model a connection error or a time-out. The watcher lets
the error go on to the check exactly as today, so that chapter keeps its
scan and is judged again later (2.3's behaviour). The job's stop then
ends the run before the next chapter. No request is sent to a server
known to be gone.

**Other errors are not "gone".** A bad or unreadable reply, or one
chapter that makes the model fail, still leaves that chapter's scan and
the run goes on, as 2.3 does and its test checks
(`test_a_model_error_on_one_chapter_does_not_stop_the_rest`).

**What you see** (scorecard and status-bar line, no box):

> ⚠ Book check waiting: the model server stopped answering at chapter 13
> of 40 ("Couldn't reach the server at http://…"). 12 chapters are kept.
> Trying again every 5 minutes · Resume now · Cancel

The same words go to the status bar once as a notice (`notify.notice`,
D.9), and are kept in Help ▸ Recent messages.

**Trying again.** The job's state becomes `waiting`. Every 5 minutes it
asks the server for its list of models (`model_server.list_models`, a
ten-second question, no model work); for a cloud model it simply tries
the next request. When the server answers, the job carries on by itself
and says "The model server is back; carrying on at chapter 13." After 12
hours of no answer it stops trying and stays paused ("Paused: the model
server has not answered since 21:40"). **Resume now** tries at once.

**Refusals are not retried.** A wrong address or a refused key (`401`,
`403`, `404`) will not mend itself, so the job pauses with the server's
own message and does not try again until you press Resume (open question
2).

**A hung server.** A request to the server waits up to 15 minutes
(`model_server.DEFAULT_TIMEOUT`, set long for a 120B model). The job
does not shorten it, so a server that hangs rather than refuses is
noticed after that wait.

### 9. Pause, resume and cancel

All on the scorecard, using what is there today:

| While the job is | The Check readiness button reads | The progress row says |
|---|---|---|
| running | **Pause** (today "Stop"; open question 5) | "Chapter 12 of 40 · about 2 hours left", the chapter being judged (as today) |
| waiting in line | **Pause** | "Waits for the Main manuscript check" |
| paused or waiting for the server | **Resume** | the reason (§7, §8), and a **Cancel** link |
| none | **Check readiness** | hidden (as today) |

- **Pause** stops after the request in hand, keeps every chapter done,
  and marks the job paused "You paused it". It stays paused across a
  restart.
- **Resume** carries on from the next chapter not yet judged.
- **Cancel** (a link in the progress row, shown only while paused or
  waiting) ends the job. Every chapter judged so far is kept; nothing is
  undone. Starting "Check the book with the model…" again later starts a
  new job, which again carries on from where judging stopped.
- **Starting a new check while one is paused** resumes the paused one
  rather than making a second.

The status-bar line has no controls of its own: clicking it shows the
scorecard (`screen_groups.show(main_window, grader_widget)`, so it raises
the Critique's own window when it is out).

### 10. How progress is shown, without a new window

1. **The scorecard's progress row**, exactly as 2.3 built it (the bar,
   "Chapter 12 of 40 · about 2 hours left", the chapter being judged), and
   the grid filling as each chapter finishes. When the scorecard is
   opened part-way through a job, it shows the job's state at once and the
   grid as stored so far.
2. **One line at the right of the main window's status bar**, there only
   while a job is unfinished, or finished and not yet looked at:
   - "📖 Book check · 12 of 40" (running)
   - "📖 Book check · waits its turn" (in line)
   - "⏸ Book check paused · 12 of 40"
   - "⚠ Book check waiting for the model server"
   - "✓ Book check done · see the scorecard" (until clicked)

   Its tooltip gives the manuscript and the full reason. This line lives
   beside the passing messages D.9 put in the status bar (the same place
   `notify` puts **Show file**) and does not cover them.
3. **Moments that matter**, once each, as quiet status-bar notices
   (`notify.notice`): the server went away, the server came back, the
   check finished ("Book check done: 40 chapters judged"), the check
   stopped with an error. Each is kept in Help ▸ Recent messages, so one
   that happened overnight is still there in the morning. No box opens.

### 11. The writer's text (rule 15)

**A job never changes the writer's text; it only adds results.**
- It reads chapters (the open chapter's text from the editor, the others
  from the project in memory, as 2.3 does). It writes only the readiness
  file (results, as today) and the job file. It never writes a chapter
  file, a `revision_NNN.md`, the project file or anything else of yours,
  and never goes through `_replace_span`.
- **Late results are checked before they land:** each result is stored
  against the fingerprint of the text it was made for. If you edit a
  chapter while it is being judged, its result is for the old text; the
  scorecard treats that chapter as changed (as it does today) and the job,
  or the next check, judges it again. A result is never shown against text
  it was not made for.
- Corrections the model finds are ordinary flags (2.3); accepting one is
  your click, through the editor, with its undo (rule 5).
- The safety check (`scripts/check_project_safety.py`) is run before and
  after 8.1b is tried, as rule 15 asks; the new job file sits beside the
  project and is covered by the folder comparison.

### 12. Tiers and settings (rules 1, 2 and 9)

- **No model:** no job. The scan runs as today; "Check the book with the
  model…" is hidden.
- **On-device model:** a job, giving way to you (§6).
- **Cloud model or your own server:** a job; "can't be reached" handled
  as in §8.
- **No new setting, page or picker.** The Critique's model is used; the
  background option is the existing one. Prompts stay as they are (rule
  9; server prompts wait for 8.3).

same.

### 14. How the code is arranged (rule 14)

All in new, small modules; no new copy of the background-thread pattern
or the provider list.

| Module | What it holds | Qt? |
|---|---|---|
| `src/data/job_store.py` | the job file: `path`, `load`, `save`, `open_jobs`, `update(project, job_id, **fields)`, through `safe_store` and `state_files` | No |
| `src/ai/book_check_job.py` | the work for kind `book_check`: wraps `book_report`; the model watcher (`watch(llm)` → passes every call through, forwards every attribute so `is_local_llm` and the model name still read right, notes "can't be reached"); `unreachable(error)` and `refused(error)`; the give-way pause for an on-device model | No |
| `src/ui/job_queue.py` | the runner, made once by the main window: the line of jobs, start / pause / resume / cancel, the retry timer, the two-minute wait after opening, keeping the Mac awake, the status-bar line, the crash-log line; signals the scorecard listens to | Yes |

Changes elsewhere: `ScorecardWidget` asks the runner instead of running
the work itself (`start_model_check`, `_background_tick`, `refresh(judge=
True)`, `_on_check_clicked`), and shows the runner's state in its
existing row. `main_window.py` gains only the few lines that make the
runner, hand it the project on open and switch, and pause it on quit.
`tests/conftest.py` redirects the job file. Kinds are a small table in
`job_queue` (kind → work function), so later kinds add one line.

### 15. Later job kinds (not built in 8.1b)

- **P.7, the reader's eye for the whole book:** a chapter-by-chapter read
  that can reuse each chapter's cached result, the same shape as the book
  check. A natural second kind.
- **8.2, the editorial letter:** one long request; worth a job on the
  server only if a single request turns out to take many minutes.
- **The detailed critique** of many chapters: already resumable through
  `critique_resume`; could become a kind later.
- **8.3** is measurement by script and is not a job.

### 16. Tests 8.1b writes

Every test with `HOME` in a scratch folder, temporary stores, a fake
model and a fake server, never a real one.

1. **Interrupted half-way, resumes from the next chapter.** A job over
   four chapters is stopped after two (the runner thrown away, as if the
   app had quit); a new runner opened on the same project carries on; the
   model sees no prompt for chapters 1 and 2; the book ends fully judged.
2. **The server goes away part-way.** A fake server that stops answering
   at chapter 3: the job is `waiting`, the message names chapter 3 of 4
   and the server's words, chapters 1 and 2 are kept, no request is sent
   for chapter 4, and no box opens.
3. **The server comes back.** The fake probe answers; the job carries on
   by itself from chapter 3 and finishes.
4. **Refusals are not retried.** A `401`: paused with the server's
   message, no probe timer.
5. **Other errors carry on.** A bad reply on one chapter leaves its scan
   and the job goes on (2.3's behaviour kept).
6. **Pause and resume.** Pause keeps finished chapters, survives a
   restart as paused (not carried on by itself), and Resume finishes.
7. **Quit, then open.** Quitting marks it "The app was closed"; opening
   the project carries it on after the wait (the wait shortened in the
   test).
8. **A crash.** A job file left `running` with no "closed" stamp carries
   on and writes one line to `crash.log`.
9. **Two jobs never run on the on-device model at once.** Two jobs
   started (main manuscript and a novella): the second waits; a fake
   on-device model records that no two requests overlap.
10. **The job gives way.** With a fake on-device model, a request from
    another feature made during a job runs before the job's next request.
11. **No second program.** Starting, running and resuming a job starts no
    process other than the keep-awake helper (checked with the process
    calls replaced).
12. **The writer's text is untouched.** After a full job, every chapter
    file and the project file are byte-for-byte the same; only the
    readiness file and the job file changed.
13. **An edit during a job.** A chapter changed while the job runs is
    counted as still to judge afterwards (`model_work`), and its result is
    not shown against the new text.
14. **Two projects.** A job in project A is paused when B is opened; B's
    files are untouched; A carries on when reopened.
15. **The job file.** Missing or empty: no job. Unreadable: set aside,
    you are told, no job, not saved over. Newer format: read, never
    written.
16. **Older versions.** A project saved before the piece opens, saves and
    reopens with every chapter the same, with and without a job file
    beside it (rule 11).
17. **Progress shows.** The scorecard row and the status-bar line read
    "12 of 40"; the line is hidden with no job and stays "done" until
    clicked; clicking it shows the scorecard; no new top-level window;
    the harness counts are unchanged.
18. **The background option** adds a quiet job only when chapters changed,
    and none while a job is unfinished.
19. **A job that dies** is marked failed, says so on the scorecard, and
    writes to `crash.log`; finished chapters are kept.
20. **Keeping awake** starts with a running job and stops when it pauses
    or finishes (the helper replaced).
21. **Existing tests unchanged:** `test_book_model_run` (except the
    button's label if open question 5 says "Pause", one line, explained),
    `test_background`, `test_state_files`, `test_readiness*`.

### 17. Open questions for the writer

1. **Carrying on after a restart.** Should an unfinished check carry on
   by itself two minutes after the project opens (recommended), or wait
   for you to press Resume? And should quitting with a check running ask
   first? Recommended: no question; it carries on next time, and the
   status-bar line tells you.
2. **When the server goes away.** Try again every 5 minutes for up to 12
   hours, then stay paused (recommended)? Or pause at once and wait for
   you? Refused keys and wrong addresses are never retried either way.
3. **Keeping the Mac awake while a check runs.** Recommended: yes, only
   while a job is running (the screen still sleeps; a closed lid still
   sleeps). Or leave sleep alone?
4. **The on-device model.** Allow jobs on it, taking turns with you as in
   §6 (recommended), or run jobs only on the server or a cloud model?
5. **"Stop" becomes "Pause".** The button already stops and keeps
   everything; with a job it pauses and can resume after a restart, so
   "Pause" / "Resume" says what it does. Recommended: rename (one line of
   2.3's test changes with it). Or keep "Stop"?
6. **The status-bar line on every screen.** Show it while a job exists
   (recommended), or only on the scorecard?
7. **Scripts and the on-device model.** The queue cannot stop a script
   run from the Terminal while the app has the on-device model loaded,
   which is what crashed the app. A small later piece could have the app
   leave a marker while it holds the on-device model, and have the
   measurement scripts refuse to start until it is closed. Recommended:
   yes, as its own small piece after 8.1b; until then, decision 12 stands.
8. **Switching project pauses the job.** Recommended: yes, and it carries
   on when you reopen that project. (Running a check for a project that is
   not open would need it loaded in the background, which risks the two
   projects touching.)
