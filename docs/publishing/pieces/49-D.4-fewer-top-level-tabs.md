## Phase context

Each of these lowers the counts recorded in 0.2. All follow rule 11:

- Each piece starts with a **capability checklist** of everything the old
  screen can do, and is not done until each item has a home in the new one.
- The replacement is built **alongside** the old screen. The old one is retired
  in a separate small step, after you have used the new one on both projects
  and agreed.
- Anything moved leaves a pointer, and shortcuts keep working.

## The piece

- **Decided:** merges are fine. The grouping itself is settled in 0.2.
- **The writer gets:** the ten top-level tabs grouped into five, with the
  existing screens unchanged inside them. Settled in 0.2:

  | Group | Screens inside |
  |---|---|
  | **Write** | Write |
  | **Story** | Plot, Characters, World |
  | **Revise** | Critique (with the scorecard), Prose Profile, Attributions |
  | **Publish** | Publishing |
  | **Studio** | Visuals, Video Studio |

  A group with one screen shows no inner tab bar, so Write and Publish look
  as they do today. Screens keep their names inside their group.
- **Simplest, nothing lost:** the writer asked for the simplest interface
  possible without cutting any feature. Capability checklist: each of the ten
  screens, how it is reached today (tab, menu items such as Review → Open
  Critique Tab, signals that switch tabs such as "📝 Open in writer" or Go to
  line), and how it is reached afterwards. Every code path that calls
  `tab_widget.setCurrentWidget(...)` must still land on the right screen.
- **Detaching:** today any top-level tab can be detached in Multi-Window Mode
  (right-click → Create New Window). Afterwards the writer can detach a whole
  group or a single screen inside it, the same way.
- **Detachable tabs stay:** any screen that can be detached into its own window
  today can still be detached after grouping, and a saved window layout from
  before the change still opens. Read
  [multi_window_architecture.md](../../multi_window_architecture.md) first.
- **Backwards compatible:** each old tab is still one click from its group,
  shortcuts still open it, and the app remembers the last tab used.
- **Done when:** the agreed grouping is in place and nothing is unreachable.

- **Data safety:** a window layout saved before the change still opens. If a
  saved layout names a tab by its old position, it is mapped to the same
  screen in its new place.

## What has changed since this brief was written

_Added 24 November 2026, after phase 3, D.3 and 2.5 were built. Read the Outcome of each piece named here._

- **There are now two ways to put the Critique in its own window.** The old
  one: Multi-Window Mode, right-click a tab → Create New Window. The new
  one: "⧉ Own window" on the Critique's top row and "Critique in Its Own
  Window" in the Critique menu (`src/ui/critique_window.py`, 2.5), which
  tiles it beside the main window and remembers where it was left.
- **This piece makes them one.** Either the "⧉" route calls the Multi-Window
  code, or Multi-Window's detach uses the same mover, for every screen. One
  mechanism, both entries kept (rule 14, decision 10).
- **`critique_window.PopOut` wraps the Critique's contents in one body
  widget** and leaves `grader_widget` as the tab's page, so
  `setCurrentWidget(self.grader_widget)` still works. Grouping must keep
  that true: when the Critique is out, choosing it raises its window.
- **Added 24 November 2026 by D.6.** The Write side panel has three tabs
  (Planner, Feedback, Companion); the Style tab is retired. Code that opens
  a side-panel tab by number goes through `retired_screens.panel_tab`
  (the old four-tab numbers; the Style tab's 1 opens the Companion). The
  same pattern fits the top-level tabs: map each old index to its screen in
  one function and test every old value. The harness counts menus by
  decision 11 (`GROUPED_MENUS` in `scripts/screen_harness.py`): a submenu of
  one closely related group is one entry, so grouping tabs under a menu
  counts each distinct screen.
- **Capability checklist additions:** the pop-out button, its menu entry,
  the "Show it · Bring it back here" note on the tab, the saved window
  position (`critique_window/geometry` in settings).
- **Added 24 November 2026: one way to detach, and one fewer button.** When
  the two mechanisms are one, the "⧉ Own window" button on the Critique's
  top row goes (it was added in 2.5 and replaces nothing). What stays:
  "Critique in Its Own Window" in the Critique menu, right-click a tab →
  open in its own window (for every screen, without first switching on
  Multi-Window Mode), and the "Show it · Bring it back here" note on the
  tab. Tiling beside the main window the first time, and remembering the
  window's place, apply to every detached screen.
- **Updating:** `critique_window/geometry` and `critique_window/out` in
  settings are still read. A layout saved by Multi-Window Mode before this
  piece still opens. View ▸ Multi-Window Mode stays in the menu and keeps
  working, as a shortcut.
- **Added 24 November 2026 by D.8 (first session).** The Critique (`GraderWidget`) and the Settings dialog set `plain_qss` on themselves so their buttons are plain, with one `PRIMARY_BUTTON` each ("Check readiness" in the scorecard; "💾 Save"). A detached or regrouped screen keeps this, since it is the widget's own style sheet. A new group container should not set a `QPushButton` rule of its own, or it would be overridden by these.

## Build notes

_Added 24 November 2026 so a fresh session can finish this piece without searching. Names were checked against the code on that date; if one has moved, find it with a search and say so in Outcome._

- **Read first:** `src/ui/window_manager.py` (`WindowManager`),
  `src/ui/secondary_window.py` (`SecondaryWindow`), `_detach_tab_to_new_window`
  and `_toggle_multi_window_mode` in `src/ui/main_window.py` (about line
  15040), `src/ui/critique_window.py`, and
  [multi_window_architecture.md](../../multi_window_architecture.md).
- **Every place that switches tabs:** search `main_window.py` and `src/ui`
  for `tab_widget.setCurrentWidget(`, `tab_widget.setCurrentIndex(`,
  `tab_widget.indexOf(` and `tab_widget.widget(`; `_on_tab_changed` compares
  `index == 0` for Write. List them all in the capability checklist with
  what each does afterwards.
- **Build:** a new small module that owns the grouping: given a screen
  widget, show it (select its group, then its inner tab, or raise its
  window if detached). The call sites change to that one call.
- **The Critique** keeps `grader_widget` as its page (see 2.5's Outcome).
- **Saved layouts:** find where Multi-Window Mode stores which tabs are in
  which window and how a tab is named there. If it stores positions, write
  the mapping from each old position to its screen and test every one.
- **Tests:** each of the ten screens reached from its tab, its menu entry
  and its signal; a layout file saved before the piece opens with each
  screen in a window; the app remembers the last screen used; the Critique
  detached by either entry comes back the same way.
- **Stop and report if** a saved layout cannot be mapped without guessing.
