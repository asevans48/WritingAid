## The piece

- **Why:** double-clicking a cell in the Critique's readiness check crashed
  the app. macOS's report showed a crash inside one of our click handlers
  while Qt was still finishing the mouse release on the table's header. It
  could not be reproduced with simulated clicks.
- **The writer gets:** the crash gone, or, if it is not, a file that says
  where in the Python code it happened.
- **Done when:** the writer has double-clicked cells, chapter names and check
  names in the main manuscript and a novella without a crash; or a trace
  from the log has led to the real cause and that is fixed.
- **If it crashes again:** read the end of `~/.creativeos/crash.log`, fix the
  handler it names, and add a test that makes the same call.

## Outcome

**Built 24 November 2026.**

- **Clicks handled after the event.** In `src/ui/scorecard_widget.py`,
  `cellClicked`, `cellDoubleClicked` and the vertical header's
  `sectionClicked` and `sectionDoubleClicked` run their handlers through
  `QTimer.singleShot(0, …)`, so a handler that opens a chapter or redraws the
  table no longer runs inside Qt's mouse event.
- **Crash log.** `_record_crashes()` in `main.py` turns on Python's
  `faulthandler` for every thread, writing to `~/.creativeos/crash.log` with
  a line for each start.
- **Tests:** the full suite; a script double-clicking every header and cell
  in the real main window reported no errors.

**Not confirmed:** the writer has not yet reported whether the crash is gone.

**For later pieces:** other tables and lists that open something on a click
(the chapter list, the Companion's lists) may need the same treatment. Do it
when a crash log names one, not before. The log is also the place for a
failed background job to leave a trace (8.1).
