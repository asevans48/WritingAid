## The piece

- **Why:** the editor's **🔍 Analyze ▾** menu runs six AI analyses, and each
  shows its result in its own window (`ProseAnalysisDialog` or
  `PromiseCheckDialog` in `src/ui/manuscript_editor.py`). Those windows offer
  only Copy to Clipboard and Close: nothing is saved, rated or kept in
  critique history. The Critique tab already does most of the same work as
  reports. Agreed in 0.2: analyses live in one place.
- **The writer gets:** each Analyze ▾ item stays in the menu, as a shortcut. It
  runs the matching report on the current chapter and shows the result in
  the Critique tab, where it can be rated, saved and found again.
- **Capability checklist:** each of the six analyses and its new home.

  | Analyze ▾ item | Today | Becomes |
  |---|---|---|
  | Promises && character consistency | `_check_promises`, `PromiseCheckDialog` | a new report kind, keeping its prompt |
  | Prose — tone, style && voice | `_analyze_prose`, `ProseAnalysisDialog` | the Voice and Style reports, or a new "Prose profile fit" report if they do not cover its comparison against the Prose Profile targets |
  | Characters | `_analyze_characters` | the Characters report |
  | Worldbuilding | `_analyze_world` | the Worldbuilding report |
  | Plot && pacing | `_analyze_plot` | the Plot and Pacing reports |
  | Writing hints | `_request_ai_hints`, `PromiseCheckDialog` | a new report kind, keeping its prompt |

  Where an existing report covers less than the analysis does, the analysis's
  prompt becomes its own report kind. The writer must not get a weaker
  result than today.
- **Also stays:** "Critique this chapter (all reports)" and "Check
  consistency…" in the same menu, unchanged.
- **Build:** the new report kinds in a new small module, called from the
  Critique's report runner. The six slots in `manuscript_editor.py` shrink to
  a call that switches to the Critique and runs the report (rule 14: that
  file is over 3,000 lines).
- **Tiers:** with no model, each item says so in the Critique tab in one line,
  and shows whatever the scan reports offer. It never shows an empty window.
- **Trial, then retire:** the old windows stay reachable during the trial,
  through a "Show in a window (old)" choice. They are retired only after you
  agree.
- **Done when:** each of the six items produces a rated, saved report in the
  Critique tab; the old windows still work; existing tests pass.

- **Data safety:** new report kinds are added to critique history without
  changing how existing entries are stored or read (rule 15). History written
  before the change still loads. A test loads an old history file, adds a
  new-kind report, saves and loads it again.
- **Older versions of the app:** history (`critique_history.json`) keys each
  report by its `ReportType` value, and saved critiques may turn that value
  back into a `ReportType`. An older app meeting a new value it does not know
  must not fail or lose the file. Before adding a kind, check every place
  that parses a stored report type (`critique_history.py`,
  `CritiqueMetadataStore` and save/load in `grader_widget.py`). If an older
  version would reject the new value, store the new reports where the older
  version skips them, and say how in *Outcome*.

## What has changed since this brief was written

_Added 24 November 2026, after phase 3, D.3 and 2.5 were built. Read the Outcome of each piece named here._

- **The Critique can be in its own window** (2.5). "Switch to the Critique
  and run the report" must use `tab_widget.setCurrentWidget(grader_widget)`,
  which brings that window forward when it is out. Do not reparent or
  re-create the Critique.
- **Reports can link to the text** the way the readiness issues do
  (`show_requested` → the revision controller's `show_passage`). Where a new
  report kind quotes the chapter, make the quote a link.

## Build notes

_Added 24 November 2026 so a fresh session can finish this piece without searching. Names were checked against the code on that date; if one has moved, find it with a search and say so in Outcome._

- **Read first:** `ReportType` in `src/ai/chapter_analysis_agent.py` (about
  line 879); the report runner and results tabs in `src/ui/grader_widget.py`;
  `critique_history.py`; in `src/ui/manuscript_editor.py`: `_check_promises`,
  `_analyze_prose`, `_analyze_characters`, `_analyze_world`, `_analyze_plot`,
  `_request_ai_hints`, `ProseAnalysisDialog`, `PromiseCheckDialog`.
- **Order of work:** (1) for each of the six, compare its prompt with the
  existing report's and write down what the existing report lacks; (2) add
  report kinds only where something is lacking; (3) point the menu items at
  the Critique; (4) add "Show in a window (old)".
- **Do not run a model while the app is using the on-device model.** Tests
  use a fake model that returns a fixed reply.
- **Tests:** each item produces a saved report found again in history; an
  old history file loads, gains a new-kind report, saves and reloads; code
  that parses a stored report type meets an unknown value without failing;
  with no model, each item shows one line and no empty window.
- **Stop and report if** an older version of the app would reject a history
  file holding a new kind and there is no place to store it that the older
  version skips.
