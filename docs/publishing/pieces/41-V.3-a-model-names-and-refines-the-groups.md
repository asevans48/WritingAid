## Phase context

**The idea.** Ratings stay in one shared store, so everything rated in any
project keeps teaching the app. Each rating is tagged with the voice of the
writing it was given to. Ratings fall into a small number of voice groups.
When the app writes a rewrite, it learns first from ratings in the same voice
group as the passage, whichever project they came from. Two books in different
voices stop colouring each other; two in a similar voice help each other; and
one book with several narrators gets a group for each.

**My reading of "broad, manageable".** Broad: shared across projects, with a
few large groups, not many small ones. Manageable: the writer can see the
groups, rename them, move a rating, merge two groups, and remove ratings.
Correct this in the review notes if you meant something else.

## The piece

- **The writer gets:** with a model set up (local, server or cloud), each group
  gets a short, human name and a one-line description from a few sample
  passages. The model is also asked about borderline ratings and whether two
  groups are really the same voice.
- **Limits:** the model proposes; nothing is merged or moved without the writer
  agreeing in V.5. Names given by the writer are never overwritten.
- **Model:** the one Rephrase already uses (rule 2). Compact prompt for local
  models, a few short samples per group.
- **Tiers:** without a model, the plain-words descriptions from V.2 stand.
- **Done when:** groups have names and a failed or unreadable reply changes
  nothing.

## Outcome

_Built 25 November 2026. No real model was run: every test and check used a
fake model. The first real trial is the writer's._

**What was built.** With the Rephrase model set up, each group V.2 made or
merged, and each of the writer's own groups left without a name, gets a
short name (2–4 words) and a one-line description, written from a few of
its rated passages. The name appears in V.5's tree as "Name — line"; the
plain-words measures move to the tooltip ("Measured: …"). A writer's name
is never changed (also when the writer renames the group while the model
is thinking); a merged group whose part had the writer's name keeps it; an
unnamed merge is named afresh. Two groups never get the same name (the
prompt lists the names taken). A failed, empty or unreadable reply changes
nothing (the groups file is byte-for-byte the same); the group is tried
again next time. Without a model the plain-words description stands.

**Proposals only (shown by V.5 with Accept · Decline).**
- *Borderline pairs*: two groups kept apart whose average separation is
  between `SAME` and `APART` (not clearly one voice, not clearly two). The
  model reads samples of both and says SAME yes/no. "Yes" adds "The model
  reads “A” and “B” as one voice. Merge them?" At most 2 questions a run;
  each asked once until the groups' sources change.
- *More than 8 groups*: the model is shown the 3 closest pairs of app-made
  groups (one sample each) and picks the most alike; V.2's "more than 8
  voices" merge suggestion then names that pair (still hidden if the merge
  would be loose). Declined: V.2's own pair comes back.
- Borderline single *ratings* are not asked about: a rating follows its
  source (V.2), so the source-level questions cover it.
- The verdicts are kept in the groups file under `model_advice` (an older
  app ignores the key); they survive regroups and are ignored once the
  groups they were about have changed.

**The model and not colliding.** `word_suggest.get_llm()` (the Rephrase
task model, else the default; rule 2). An on-device model is **never
loaded for this**: it is used only when it is already in memory (built by
Rephrase, or resident in the MLX cache). It is used only while no other
feature is generating: `mlx_utils.MLX_GENERATE_LOCK` is tried without
blocking, for up to 30 s, then the run stops ("busy") and waits for the
next one. One short call per group (70 tokens; 60 for a verdict; 12 for
the pair), the lock released between calls. Local models get a compact
prompt (3 samples of 350 characters; otherwise 4 of 600). Nothing is
configured: no model, no call.

**When it runs** (always on a background daemon thread, never the GUI
thread): after V.2's start-up check, in the same thread (35 s after
start-up, after V.1's fingerprints); when the writer opens Training Studio
▸ Browse rows ▸ "rated rewrites, by voice" (at most every 2 minutes); and
after "Rebuild the groups". The tree refreshes when names arrive. Only for
the app's own ratings database.

**The prompt** (naming): "Passages written in one voice: 1. … 2. … /
Measured: ‹V.2's description›. / Names already used (choose another): … /
Name this voice in 2 to 4 words (for example: Wry first-person narrator).
Then describe it in one sentence of at most 20 words: how it is written,
not the story. Answer exactly: NAME: … DESCRIPTION: …"

**Files.**
- New `src/ai/voice_naming.py`: `name_groups(db=None, llm=None, wait=30)`
  → `{named, failed, asked, busy, model}`; `start_naming(db, on_done,

**Tests.** A readable reply names each new group from its own passages; a
