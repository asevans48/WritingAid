## Why

The safety check (0.3) found that both projects open, save and reopen with
nothing lost. Reading the save code turned up five weaker spots. None is known
to have caused a loss, and each is about an interrupted save, an unreadable
file or a later mistake, not about normal use. They matter now because the
plan adds more stored files, and new stores must not copy these habits.

## The piece

- **1. Chapter files are not written safely.** The project file is written to a
  temporary file and swapped in, so an interrupted save cannot damage it. A
  chapter's text is written straight over the existing file. If the app or
  the drive stops mid-write, the chapter file can be left cut short. A backup
  is taken first, so the text is recoverable, but only by hand.
  - **Do:** write chapter and outline files the same way as the project file:
    to a temporary file in the same folder, then swap. On failure, leave the
    old file in place and report the error.
- **2. The three rolling backups cover minutes, not days.** Each chapter keeps
  its three most recent backups. In Teller County these are often seconds or
  minutes apart, so a mistake saved three times pushes every good copy out.
  - **Do:** keep the three most recent as now, and also keep the first backup
    of each day for the last fourteen days. Never delete a backup that is the
    only one holding text when the current file is empty.
- **3. Unknown fields survive only at the top level.** If a later version adds a
  field inside a chapter or character and an older version then saves the
  project, the field is dropped.
  - **Do:** make the nested parts of the project keep fields they do not
    recognise, as the top level already does. Confirm with a test that a
    project file carrying an unknown field inside a chapter, a character and a
    novella still has it after open, save and reopen.
- **4. An unreadable side file is treated as empty, then saved over.** The
  files beside a project (`companion_state.json`, `critique_history.json`)
  are read with "on any error, start empty". If one cannot be read for a
  moment (a drive hiccup, a half-written file), the next save writes the
  near-empty data over it. That would lose notes, section choices, style
  preferences and critique history.
  - **Do:** new `src/data/safe_store.py` with `load(path, default)` and
    `save(path, data)`. `load` tells "missing" from "unreadable". When a file
    exists but cannot be read, it is renamed aside
    (`name.unreadable-YYYYMMDD_HHMMSS`), the writer is told once, and only
    then does the app start fresh. Move `companion_state` and
    `critique_history` onto it without changing their file names or contents.
- **5. Side files and settings are written in place.** An interrupted write can
  leave them cut short.
  - **Do:** `safe_store.save` writes to a temporary file in the same folder
    and swaps it in. Use it for the two side files. For the settings files
    (`~/.writer_platform/ai_config.json`, `~/.creativeos/config.json`), make
    the existing save functions write the same way, changing nothing else.
- **Every later store uses `safe_store`:** the readiness file (1.2), dismissals
  (3.3), job state (8.1) and anything else the plan adds.
- **Not in this piece:** changing the file layout, the project format version,
  or where anything is stored.
- **Removable drive.** Both projects are on a USB drive formatted as exFAT.
  Pulling the drive or losing power during a save is the likeliest way to lose
  work, and a single drive is a single copy. This piece cannot fix that. Two
  habits do: take a checkpoint in the app before each plan piece is tried on a
  real project, and keep a second copy of the project folders off the drive.
- **Tests:** an unreadable side file is set aside, not overwritten; a missing one
  starts empty without a warning; an interrupted side-file or settings write
  leaves the old file whole; an interrupted chapter write leaves the old text in place; backup
  pruning keeps one per day and never removes the last copy with text; unknown
  nested fields survive; `tests/test_project_compat.py` passes unchanged.
- **Done when:** the tests pass, `scripts/check_project_safety.py` still passes
  on both projects, and the stores comparison shows nothing lost.

## Outcome

**Status:** done. All five fixes are in, tested, and checked on both projects.

**New modules:**

- `src/data/safe_store.py`, the shared store every later piece uses:
  - `write_text(path, text)`: writes to a temporary file in the same folder,
    flushes it to disk, then swaps it in. It keeps the old file's
    permissions. On failure the old file is left whole and the error is
    raised.
  - `write_text_if_changed(path, text)`: the same, but skips files that
    already hold that text.
  - `load(path, default, expect=None)`: a missing file gives `default`,
    quietly. An unreadable file (cannot be read, not valid JSON, or not of
    type `expect`) is renamed to `<name>.unreadable-YYYYMMDD_HHMMSS`, the
    writer is told once, and `default` is returned. If even the rename
    fails, the file is blocked.
  - `save(path, data, indent=1)`: a safe write. It refuses to write over a
    blocked file and returns False.
  - `set_notifier(fn)`: how the app is told. Notices raised before a
    notifier is set are delivered once it is.
- `src/models/chapter_backups.py`: `to_remove(backups, saving_empty=...)`
  holds the backup rule.
- `src/models/keep_unknown_fields.py`: `keep_unknown_fields(WriterProject)`
  switches the 99 models reachable from the project (33 in `project.py`, 47
  in `worldbuilding_objects.py`, 19 in `video_studio/models.py`) to keep
  fields they do not recognise. It rebuilds children before parents. It
  is called once, at the end of `project.py`.
- `src/ui/store_notice.py`: `install(main_window)` shows each notice in a
  non-blocking warning box and the status bar. It carries notices from
  background threads through a Qt signal.

**Changed:**

- `src/models/project.py` (2,613 lines, under the 3,000 limit):
  - every chapter, revision and outline write goes through `safe_store`.
    The repeated saves in `save_active_revision_to_file`,
    `save_content_to_file` and `save_plan_to_file` skip unchanged files;
    `add_revision` and the legacy migration write new files;
  - `_save_working_backup` prunes with `chapter_backups.to_remove`;
  - the last lines call `keep_unknown_fields`.

  File names, folders, the project file format and the format version are
  unchanged. `save_project`'s own write of the project file was already
  safe and is not touched.
- `src/data/companion_state.py` and `src/data/critique_history.py`: `load`
  and `save` use `safe_store`, with the same file names and the same JSON
  layout (`indent=1`). Their public functions are unchanged.
- `src/config/ai_config.py` (`AIConfig.save_settings`) and
  `src/config/creativeos_config.py` (`CreativeOSConfig.save`): safe writes,
  with the same JSON options as before. Nothing else changed.
- `src/ui/main_window.py`: two lines in `__init__` install the notice.

- Stores comparison, before and after: **stores intact** (11 stores).

**Worth knowing:**

- **The revert submenu gets longer.** The chapter list's *Revert to Saved
  Copy* submenu lists every backup, so it can now show up to about 17 dated
  copies instead of 3. These are restore points, not new controls.
- **Fix 3 protects data from newer versions only.** The version of the app
  you use today already drops unknown nested fields; nothing can change that
  in a copy already installed.
- **Unknown fields are now kept everywhere,** including keys in AI-produced
  JSON brought in through Import JSON Data. Before, those were silently
  dropped; now any key the model does not know is stored with the item.
  This is harmless, but such files can carry extra keys. None of the
  validators that run on load read fields a model does not declare, so a
  kept field cannot bring back old data.
- **Unchanged files are no longer rewritten** when the project is saved, so
  their modification times stay put. Nothing in the app reads those times
  (backups are named by time stamp).

**Left out:**

- **Settings that cannot be read are still treated as empty.** If
  `ai_config.json` or `~/.creativeos/config.json` cannot be read,
  `_load_settings` falls back to the defaults, and the next save writes
  them over the file, as before. The brief said "changing nothing else" for
  settings, so they were not moved onto `safe_store.load`. Doing so is a
  small follow-up worth considering.
- **Other settings-like files** still write in place:
  `~/.creativeos/trained_models.json` (the trained-model registry,
  `creativeos_config.py`) and `genai_config.json`. Each is a one-line move
  to `safe_store.write_text`.
- **The USB drive.** The piece cannot fix it. Keep a second copy of the
  project folders off the drive, and take a checkpoint before trying each
  plan piece on a real project.

**For the next pieces:** every new store uses `safe_store.load` and

(8.1). A piece that adds a store also adds it to the test set-up in
